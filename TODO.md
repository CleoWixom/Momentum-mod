## Критические баги / риски

### [BUG-01] ✅ RXFIFO_OVERFLOW не работает корректно
**Файл:** `applications/drivers/subghz/cc1101_ext/cc1101_ext.c`
**Строка:** `subghz_device_cc1101_ext_rx_pipe_not_empty()`
```c
// TODO: Find reason why RXFIFO_OVERFLOW doesnt work correctly
```
Это **оригинальный TODO** прямо в коде. `CC1101RxBytes.RXFIFO_OVERFLOW` флаг игнорируется, функция проверяет только `NUM_RXBYTES > 0`. Если FIFO переполняется, принятые данные молча теряются или портятся без какого-либо уведомления.

**Что сделать:**
- [x] Разобраться с правильным порядком чтения статусного регистра CC1101 (Status byte vs. RXBYTES register — разные адреса и режимы чтения через burst).
- [x] При обнаружении overflow — вызывать `cc1101_flush_rx()` и возвращать ошибку вызывающему, а не молча пропускать.
- [x] Добавить счётчик overflow-событий в статистику.

---

### [BUG-02] ⚠️ Утечка ресурсов в `subghz_device_cc1101_ext_is_connect()` *(частично)*
**Файл:** `cc1101_ext.c`
```c
bool subghz_device_cc1101_ext_is_connect(void) {
    bool ret = false;
    if(subghz_device_cc1101_ext == NULL) { // not initialized
        ret = subghz_device_cc1101_ext_alloc(NULL);
        subghz_device_cc1101_ext_free();   // free сразу после alloc
    } else { ...
```
`alloc()` инициализирует SPI bus handle, GPIO и запускает полную процедуру `check_init()` — это дорого. Хуже того: если `check_init()` зависнет (таймаут 100 мс), эта функция заблокирует поток на 100 мс. Также нет проверки: если `alloc` вернул `false`, `free()` вызывается на потенциально частично инициализированной структуре.

**Что сделать:**
- [x] Реализовать лёгкую `probe` функцию — только SPI acquire → читать PARTNUM/VERSION регистры → release, без полного alloc/free. *(для уже-инициализированного устройства; путь через alloc/free при NULL не переписан)*
- [x] Добавить проверку возврата: если `alloc()` вернул `false`, `free()` должен знать об этом.

---

### [BUG-03] ✅ Логика освобождения CS пина в `free()` зависит от настроек NRF24
**Файл:** `cc1101_ext.c`
```c
void subghz_device_cc1101_ext_free(void) {
    ...
    // resetting the CS pins to floating
    if(momentum_settings.spi_nrf24_handle == SpiDefault ||
       subghz_device_cc1101_ext->amp_and_leds) {
        furi_hal_gpio_init_simple(&gpio_ext_pc3, GpioModeAnalog);
    } else if(momentum_settings.spi_nrf24_handle == SpiExtra) {
        furi_hal_gpio_init_simple(&gpio_ext_pa4, GpioModeAnalog);
    }
```
`cc1101_ext` драйвер не должен знать ничего о `spi_nrf24_handle`. Это явное нарушение single responsibility — CC1101 модуль принимает решения на основе конфигурации NRF24. При изменении конфигурации NRF24 поведение CC1101 `free()` меняется неочевидно.

**Что сделать:**
- [x] Добавить в структуру `SubGhzDeviceCC1101Ext` поле `const GpioPin* cs_pin` — и сохранять CS pin при `alloc()`.
- [x] В `free()` сбрасывать только собственный CS pin, не анализируя глобальные настройки.
- [ ] Разрешение конфликта GPIO между cc1101/nrf24 вынести в отдельный GPIO-конфигурационный модуль. *(`momentum_settings.spi_cc1101_handle` по-прежнему читается в `alloc()` — следующий шаг)*

### [BUG-04] Краш в RAW view при работе с памятью
**История:** `mntm-latest: OFW: SubGHz: Fix memory corrupt in read raw view crash (by @DrZlo13)`

Краш был воспроизводим и пофикшен патчем из OFW, но корневая причина — в `subghz_scene_read_raw.c` и обработчике DMA буфера. Буфер `SUBGHZ_DEVICE_CC1101_EXT_ASYNC_TX_BUFFER_FULL = 256u` элементов делится на два полубуфера (Half/Full interrupt). При длинных RAW сигналах возможна гонка: callback вызывается пока предыдущая обработка не завершена.

**Что сделать:**
- [ ] Проверить, что DMA half/full transfer callbacks правильно синхронизированы с основным потоком.
- [ ] Рассмотреть увеличение буфера для ext модуля (512 или 1024), т.к. внешние модули могут работать с более длинными сигналами.
- [ ] Добавить defensive check: если callback вызван пока флаг `is_running` установлен — логировать ошибку и пропускать.

---

### [BUG-05] Краш при установке частот на границах диапазона
**История:** `SubGHz: Fixed crash when setting frequencies near range limits (by @Willy-JL)`

Частота принималась без санитизации, затем передавалась в CC1101 расчёты, где integer overflow / underflow вызывал некорректные значения регистров.

**Что сделать:**
- [ ] В `subghz_setting.c` добавить централизованный `subghz_validate_frequency(uint32_t hz)` — единая точка валидации для всех путей кода (UI, RPC, file load, hopper).
- [ ] При загрузке частот из файла настроек — валидировать, логировать предупреждение при пропуске невалидной записи.

## Архитектурные проблемы

### [ARCH-01] ⚠️ Глобальный singleton без защиты *(частично)*
**Файл:** `cc1101_ext.c`
```c
static SubGhzDeviceCC1101Ext* subghz_device_cc1101_ext = NULL;
```
Глобальный указатель без mutex. Все функции работают через этот глобал. Если две задачи вызовут функции одновременно — UB. На Flipper Zero это менее критично (cooperative-ish), но при использовании через RPC или notification callbacks это реальный риск.

**Что сделать:**
- [ ] Рассмотреть добавление `FuriMutex* mutex` в структуру или использование `furi_check` / `furi_assert` для явного документирования допустимых состояний. *(mutex не добавлен)*
- [x] Минимум: добавить `furi_assert` в начало всех публичных функций, проверяющий `state != Init`.

---

### [ARCH-02] Прямая зависимость драйвера от `momentum_settings`
**Файл:** `cc1101_ext.c`
```c
subghz_device_cc1101_ext->spi_bus_handle =
    (momentum_settings.spi_cc1101_handle == SpiDefault ?
        &furi_hal_spi_bus_handle_external :
        &furi_hal_spi_bus_handle_external_extra);
```
Низкоуровневый драйвер железа напрямую читает глобальные настройки прошивки. Это делает драйвер непереносимым и усложняет тестирование. Настройки уже частично передаются через `SubGhzDeviceConf`, но часть логики читает `momentum_settings` напрямую в обход конфига.

**Что сделать:**
- [ ] Расширить `SubGhzDeviceConf` (конфиг версии 1 → версии 2): добавить поле `spi_bus_handle` и `cs_gpio_pin`.
- [ ] Убрать все прямые обращения к `momentum_settings` из `cc1101_ext.c` — пусть вызывающий код (subghz app или loader) резолвит настройки и передаёт через конфиг.
- [ ] Обновить `SUBGHZ_DEVICE_CC1101_CONFIG_VER` до 2.

---

### [ARCH-03] Монолитный `subghz_txrx.c`
`helpers/subghz_txrx.c` является "швейцарским ножом": он управляет и устройством, и протоколами, и состоянием TX/RX, и настройками, и workerом. Это затрудняет изолированное тестирование и понимание code flow.

**Что сделать:**
- [ ] Выделить управление состоянием радио (`SubGhzRadioState`) в отдельный модуль.
- [ ] Отделить управление протоколами (`SubGhzProtocolHandle`) от управления железом.
- [ ] Выделить логику "разрешено ли TX на этой частоте" в отдельную функцию/модуль (частично сделано через `subghz_devices_check_tx`, но без центральной точки входа).

---

### [ARCH-04] Дублирование кода между `cc1101_int_interconnect.c` и `cc1101_ext_interconnect.c`
Оба файла реализуют один и тот же интерфейс (`SubGhzDeviceInterconnect`) с большим количеством идентичного кода. Изменение поведения требует правок в двух местах.

**Что сделать:**
- [ ] Выделить общую логику в `cc1101_common.c` / `cc1101_common.h`.
- [ ] Interconnect-файлы должны содержать только специфику int/ext (пины, SPI handle, адреса регистров если они различаются).

## subghz_worker

### [WORKER-01] Отсутствие rate-limiting при высокой плотности сигналов
`SubGhzWorker` запускается как FreeRTOS задача и обрабатывает каждый декодированный сигнал через callback. При очень плотном RF трафике (например, автостоянка с множеством пультов) очередь сообщений может насыщаться, что приводило к зависаниям (описано в mntm-011 как CPU overload при большом числе протоколов).

**Что сделать:**
- [ ] Добавить дребезгофильтр: если от одного и того же протокола/данных получен сигнал менее чем N мс назад — пропускать.
- [ ] Добавить счётчик пропущенных сообщений в статистику воркера (полезно для диагностики).
- [ ] Рассмотреть lowpass по RSSI: не декодировать сигналы ниже порогового RSSI (уже есть настройка, но применяется не на всех путях).

---

### [WORKER-02] Worker не освобождает ресурсы при exception в callback
Если callback вызывает `furi_crash` или паникует — worker остаётся в неопределённом состоянии, SPI bus может быть захвачен.

**Что сделать:**
- [ ] Обернуть вызов callback в проверку состояния: до/после вызова убедиться что `radio state` корректен.
- [ ] Worker должен уметь восстанавливаться из ошибочного состояния через `subghz_txrx_rx_end()` → `subghz_txrx_rx_start()`.

---

### [WORKER-03] ✅ Нет явного приоритета задачи
`SubGhzWorker` создаётся с дефолтным приоритетом. Для корректного приёма сигналов (особенно коротких импульсов) желателен более высокий приоритет.

**Что сделать:**
- [x] Явно задать приоритет воркера (например, `FuriThreadPriorityHigh`) и задокументировать выбор.
- [ ] Провести анализ: текущий приоритет vs. приоритет UI thread — не мешают ли они друг другу при активном рисовании.

### [CC1101-02] ⚠️ `load_custom_preset` — нет защиты от выхода за границы *(частично)*
```c
void subghz_device_cc1101_ext_load_custom_preset(const uint8_t* preset_data) {
    uint32_t i = 0;
    while(preset_data[i]) {  // останавливается на нулевом байте
        cc1101_write_reg(..., preset_data[i], preset_data[i + 1]);
        i += 2;
    }
    memcpy(&pa[0], &preset_data[i + 2], 8);  // фиксированное смещение
```
Если `preset_data` не содержит нулевого байта в пределах разумного размера — infinite loop. Если формат пресета повреждён — `memcpy` читает за пределами буфера.

**Что сделать:**
- [ ] Добавить параметр `size_t preset_data_len` в сигнатуру функции (breaking change → обновить `SUBGHZ_DEVICE_CC1101_CONFIG_VER`). *(не сделано — вместо этого добавлен cap 256 байт через макрос `SUBGHZ_CC1101_PRESET_MAX_CONFIG_BYTES`)*
- [ ] Добавить `furi_assert(i < preset_data_len - 2)` в тело цикла. *(используется условие `i < 256-2` без size-параметра)*
- [ ] Проверить что `i + 2 + 8 <= preset_data_len` перед `memcpy`. *(memcpy по-прежнему без bounds-check на PA-секцию)*

### [CC1101-03] ✅ `dump_state()` использует `printf` вместо FURI логгера

void subghz_device_cc1101_ext_dump_state(void) {

- [x] Заменить `printf` на `FURI_LOG_I(TAG, ...)`.

## subghz_history

### [HISTORY-01] Потеря истории при выходе из приложения
По умолчанию вся принятая история (до 50 записей) хранится только в RAM. При выходе из SubGHz или перезагрузке — всё теряется, если пользователь не сохранил каждый сигнал вручную.

**Что сделать:**
- [ ] Добавить опцию "Auto-save history on exit" — сохранять все несохранённые записи в папку `subghz/history/` при выходе.
- [ ] Добавить "Load previous session" при следующем открытии приложения.

---

### [HISTORY-02] Жёстко заданный лимит в 50 записей без конфигурации
`SUBGHZ_HISTORY_MAX` = 50. На практике пользователь может хотеть больше или меньше (экономия RAM vs. удобство).

**Что сделать:**
- [ ] Вынести лимит в `subghz_last_settings` как настраиваемый параметр (диапазон: 10–200).
- [ ] При превышении лимита — не молча выбрасывать старые записи, а уведомлять пользователя.

---

### [HISTORY-03] ✅ Нет дедупликации одинаковых сигналов
Если пульт нажат 5 раз подряд — в историю добавляется 5 идентичных записей (для статических кодов). Это засоряет историю.

**Что сделать:**
- [x] Для статических протоколов: если последняя запись в истории идентична новой (protocol + data + frequency) и прошло менее 2 секунд — обновить timestamp вместо добавления новой записи. *(реализовано через `code_last_hash_data` + окно 600 мс)*
- [x] Для rolling code протоколов — дедупликацию не делать (там каждое нажатие уникально). *(hash-подход автоматически обрабатывает это)*

### [QUALITY-02] Magic numbers без объяснения
В cc1101_ext.c и subghz_txrx.c встречаются числа типа `0x07`, `0x3F`, `999u >> 1` без комментариев.

**Что сделать:**
- [ ] Провести аудит всех magic numbers в `cc1101_ext.c` и `subghz_txrx.c`.
- [ ] Заменить на именованные константы с ссылками на CC1101 datasheet (Rev. E, секция X).

---

### [QUALITY-03] ⚠️ Отсутствие проверки возвращаемых значений ряда SPI-операций *(частично)*
Многие `cc1101_write_reg()` вызовы внутри функций (кроме `check_init`) не проверяют `CC1101Status.CHIP_RDYn`. Если чип завис или отключился во время работы — это не обнаруживается.

**Что сделать:**
- [ ] Добавить watchdog-like проверку: периодически (например, раз в 5 секунд в idle) читать MARCSTATE регистр и проверять что чип в ожидаемом состоянии.
- [x] В критических функциях (`set_frequency`, `calibrate`) — проверять статус и возвращать `bool`. *(`CHIP_RDYn` проверяется на каждом шаге `check_init`; `furi_check` применён в TX/RX-переходах)*
